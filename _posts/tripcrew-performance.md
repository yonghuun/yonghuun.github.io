## 프로젝트 소개

TripCrew는 관광지 검색과 여행 일정 관리를 제공하는 여행 플랫폼입니다.

저는 백엔드 개발을 담당하며 관광지 조회 API, 인증 기능, 데이터베이스 구조 및 검색 성능 개선을 진행했습니다.

## 문제 상황

약 80만 건의 관광지 데이터를 조회하는 과정에서 일부 API의 응답 시간이 길어졌습니다.

| 조회 조건 | 개선 전 |
|---|---:|
| 전체 관광지 조회 | 506ms |
| 키워드 검색 | 523ms |
| 카페 검색 | 940ms |

단순히 Redis 캐시를 추가하기보다 먼저 SQL과 데이터베이스 구조에서 병목의 원인을 찾기로 했습니다.

## 원인 분석

애플리케이션 로그와 MySQL `EXPLAIN`을 확인했습니다.

분석 결과 다음 문제가 있었습니다.

- count 쿼리에서도 불필요한 JOIN 수행
- 일부 검색 조건에서 Full Table Scan 발생
- `LIKE '%keyword%'` 검색으로 인덱스 활용 제한
- 목록 조회와 전체 개수 계산이 같은 구조에 의존

## 개선 방법

### 1. count 쿼리 분리

전체 개수만 필요한 쿼리에서는 상세 데이터 JOIN을 제거했습니다.

### 2. 검색 조건별 인덱스 적용

지역, 관광지 유형 등 자주 사용되는 검색 조건을 기준으로 인덱스를 구성했습니다.

### 3. FULLTEXT 인덱스 도입

키워드 검색을 기존 `LIKE` 방식에서 MySQL FULLTEXT 검색으로 변경했습니다.

## 개선 결과

| 조회 조건 | 개선 전 | 개선 후 | 개선율 |
|---|---:|---:|---:|
| 전체 관광지 조회 | 506ms | 52ms | 89.7% |
| 키워드 검색 | 523ms | 4ms | 99.2% |
| 카페 검색 | 940ms | 34ms | 96.4% |

## 배운 점

성능 문제가 발생했을 때 캐시나 인프라를 먼저 추가하기보다, 로그와 실행 계획을 통해 실제 병목을 확인하는 것이 중요했습니다.

또한 같은 결과를 반환하더라도 SQL의 JOIN 구조와 인덱스 사용 여부에 따라 성능이 크게 달라질 수 있다는 점을 확인했습니다.
