SafeFlow는 국내 법령과 산업재해 데이터를 연결해 사업장의 위험성평가를 돕는 프로젝트입니다. 저는 데이터·AI 파이프라인을 맡아 재해 분류 전처리, Spark 집계, 법령 검색을 순서대로 진행하고 있습니다.

이번 작업은 Jira `S15P21A404-61`의 **법령 1,294조 코퍼스 구축·청킹**입니다. 후속 RAG가 검색할 수 있도록 원문을 청크로 만들고, 임베딩 인덱스와 최소 품질 검사를 준비하는 것이 목표였습니다.

> 이 글의 수치는 2026년 9월 7일 로컬에서 공식 수집기를 다시 실행해 확인한 결과입니다. 검색 스모크 테스트는 파이프라인 이상을 찾기 위한 작은 점검셋이며, 운영 품질을 보장하는 벤치마크는 아닙니다.
{: .prompt-info }

## 왜 이 작업부터 시작했나

SafeFlow의 사고 데이터 파이프라인에는 미국 OSHA 데이터가 포함됩니다. 그렇다면 자연스럽게 “미국 데이터로 찾은 위험이 국내 현장에 맞는가?”라는 질문이 생깁니다.

법령 RAG는 이 질문에 국내 근거를 연결하는 역할을 합니다. 또한 법령 코퍼스는 OSHA 수집이나 Spark 집계 완료를 기다릴 필요가 없는 독립 작업이어서 먼저 시작할 수 있었습니다.

```text
법령 원문 1,294조
  → 구조 보존 청킹
  → 문서 임베딩
  → 벡터 인덱스
  → 위험 상황 질의 Top-K 검색
  → 후속 RAG 답변의 근거
```

## 원천 데이터를 다시 검증했다

국가법령정보 API 수집기를 실행해 7개 법령을 다시 받았습니다. 결과는 1,294조, 14개 컬럼이었고 `조문전문` 결측은 0건이었습니다.

| 확인 항목 | 결과 |
|---|---:|
| 조문 수 | 1,294 |
| 본문 결측 | 0 |
| 본문 길이 중앙값 | 257자 |
| 본문 길이 95백분위 | 1,016자 |
| 최장 본문 | 4,670자 |

명세에는 13개 컬럼으로 적혀 있었지만 실제 스키마는 14개였습니다. 구현만 맞고 문서가 틀린 상태를 남기지 않기 위해 명세도 함께 14개로 고쳤습니다.

ID도 그대로 믿을 수 없었습니다. 원천의 `조문키`는 법령이 다르면 같은 값이 반복됐습니다. 245개 키 값이 둘 이상의 법령에서 겹쳤기 때문에, 검색 문서 ID는 다음처럼 법령 ID를 포함해 만들었습니다.

```text
law_{법령ID}_{조문번호}_{가지번호}
law_001766_0036
law_007364_0037_2
```

가지번호를 별도로 넣은 이유는 `제37조`와 `제37조의2`가 다른 조문이기 때문입니다. 이 구분이 사라지면 검색 결과를 원문 조항으로 되돌릴 수 없습니다.

## 조 단위와 항 단위 사이에서 선택한 것

처음 선택지는 단순했습니다.

| 방식 | 장점 | 문제 |
|---|---|---|
| 조 단위 | 인용 단위와 같고 문맥이 온전함 | 장문 조항이 모델 입력 한도를 넘음 |
| 항·호 단위 | 검색 범위가 작고 세밀함 | 법령명·조문 제목과 상위 문맥을 잃기 쉬움 |

사용한 한국어 Sentence Transformer의 입력 한도는 128토큰입니다. 조문 길이 편차가 큰 상태에서 조 단위만 고집하면 긴 조문의 뒷부분이 잘리고, 모든 조문을 항 단위로 쪼개면 짧은 조문까지 불필요하게 분리됩니다.

그래서 **조문은 문서 ID로 유지하고, 한도를 넘는 조문만 구조 경계에서 나누는 혼합 방식**을 선택했습니다.

1. 법령명·조문번호·제목을 모든 검색 청크의 헤더에 붙입니다.
2. 조문전문의 줄바꿈으로 보존된 항·호·목을 우선 경계로 사용합니다.
3. 한 줄 자체가 긴 경우에만 토큰 수를 재며 추가 분할합니다.
4. 모델 한도보다 여유를 둔 120토큰을 상한으로 검증합니다.
5. `doc_id`는 조문 단위, `chunk_id`는 조문 아래 순번으로 관리합니다.

```text
doc_id   = law_001766_0175
chunk_id = law_001766_0175_c01
           law_001766_0175_c02
           ...
```

이 방식으로 1,294조가 3,767청크가 됐습니다. 851개 조문만 둘 이상으로 나뉘었고, 가장 긴 조문은 33청크였습니다. 모든 `search_text`가 120토큰 이하인지 생성 단계에서 검사했습니다.

## 인덱스는 단순하게 시작했다

3,767건은 전용 벡터 데이터베이스를 먼저 도입해야 할 규모가 아닙니다. 기존 프로젝트에 있던 `sentence-transformers`를 사용해 768차원 L2 정규화 벡터를 만들고 NumPy 배열로 저장했습니다.

```text
law_corpus.parquet   3,767개 청크와 출처 메타데이터
law_embeddings.npy  3,767 × 768 정규화 벡터
*_manifest.json      원천 SHA-256, 모델명, 건수, 차원
```

정규화된 벡터는 내적이 코사인 유사도와 같으므로 검색은 행렬 곱으로 충분합니다. 검색 결과에서는 같은 조문의 여러 청크가 Top-K를 점유하지 않도록 **조문별 최고 점수 청크만 남겼습니다.**

FAISS 같은 의존성을 바로 추가하지 않은 이유도 여기에 있습니다. 현재 규모에서는 단순 행렬 검색으로 동작과 품질을 먼저 확인할 수 있고, 실제 지연 시간이 문제가 될 때 인덱스 구조를 바꿔도 코퍼스 스키마는 유지할 수 있습니다.

## 스모크 테스트 10건

위험 상황을 표현한 질의 10건을 만들고, 원문 데이터에서 기대 조문 후보를 직접 확인했습니다. 하나의 상황에 여러 조문이 유효할 수 있어 단일 정답이 아니라 `expected_doc_ids` 목록으로 관리했습니다.

```json
{
  "query": "근로자가 쉬는 공간의 설치와 관리 기준을 확인하고 싶다",
  "expected_doc_ids": ["관련 법령의 복수 조문 ID"]
}
```

최종 결과는 다음과 같습니다.

| 검증 | 결과 |
|---|---:|
| assert 기반 단위 테스트 | 7/7 통과 |
| 위험 상황 검색 Hit@5 | 10/10, 100% |
| MRR | 0.650 |
| 임베딩 크기 | 3,767 × 768 |
| 로컬 인덱싱 시간 | 20.9초 |

Hit@5는 모두 통과했지만 MRR이 0.650이라는 점도 중요합니다. 기대 조문이 다섯 개 안에는 들어왔어도 항상 첫 번째는 아니었습니다. 현재 결과는 “검색 배관이 연결됐다”는 증거이고, “가장 좋은 조문이 항상 1위다”라는 증거는 아닙니다.

## 재현 순서

원천 데이터와 생성 산출물은 저장소에 올리지 않습니다. 같은 과정을 다시 실행할 수 있는 코드와 매니페스트만 관리합니다.

```bash
python -m data.collectors.fetch_law_articles
python -m ai.retrieval.law_corpus
python -m ai.retrieval.law_index build
python -m ai.retrieval.law_index smoke -k 5
```

단위 테스트는 별도로 실행합니다.

```bash
python -m ai.retrieval.test_law_corpus
```

## 이번에 얻은 교훈

첫째, **법령 검색에서는 임베딩 모델보다 추적 가능한 ID가 먼저**였습니다. 검색이 잘되어도 어느 법령의 몇 조인지 안정적으로 되돌릴 수 없으면 근거로 쓸 수 없습니다.

둘째, **평균 길이만 보고 청킹을 결정하면 긴 꼬리를 놓칩니다.** 평균은 368자였지만 최장은 4,670자였습니다. 백분위와 최댓값을 함께 본 뒤 모델 토큰 한도로 다시 검증해야 했습니다.

셋째, **10/10이라는 숫자만 쓰면 품질을 과장하게 됩니다.** Hit@5 100%와 함께 MRR 0.650, 작은 수동 점검셋이라는 한계를 같이 기록해야 다음 개선이 어디서 시작되는지 알 수 있습니다.

다음 작업에서는 이 코퍼스를 실제 E1 법령 RAG 검색에 연결하고, 질의셋을 늘려 오답 유형과 순위 품질을 따로 측정할 예정입니다. 그 전에 독립적으로 진행 가능한 Spark 위험요인 집계 작업을 이어갑니다.
