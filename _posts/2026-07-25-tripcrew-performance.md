## 프로젝트와 데이터 규모

TripCrew는 관광지 탐색과 여행 일정 관리를 제공하는 여행 플랫폼입니다. 약 80만 건의 관광지 데이터를 대상으로 검색·필터 API를 개발했습니다.

## 문제 상황

| 조회 조건 | 개선 전 |
|---|---:|
| 전체 관광지 조회 | 506ms |
| 키워드 검색 | 523ms |
| 카페 검색 | 940ms |

응답이 느리다는 이유만으로 Redis 캐시부터 적용하지 않았습니다. 캐시는 병목을 가릴 수 있고, 데이터 변경 시 정합성과 무효화 전략이라는 새로운 문제를 만들기 때문입니다. 먼저 애플리케이션 로그와 MySQL `EXPLAIN`으로 실제 병목을 찾았습니다.

## 원인

- count 쿼리에서도 상세 데이터 조회를 위한 불필요한 JOIN 수행
- 일부 조건에서 Full Table Scan 발생
- `LIKE '%keyword%'` 구조로 인덱스 활용 제한
- 목록 조회와 count가 같은 복잡한 구조에 의존

## 해결

### 조회 쿼리와 count 쿼리 분리

목록에 필요한 컬럼과 전체 개수 계산에 필요한 조건이 다르다는 점에 맞춰 두 쿼리를 분리했습니다. count 쿼리에서는 결과에 영향을 주지 않는 JOIN을 제거했습니다.

### 조건별 인덱스 적용

시도, 구군, 관광지 유형처럼 자주 조회하는 조건을 기준으로 인덱스를 적용했습니다.

### MySQL FULLTEXT 도입

키워드 검색의 `LIKE '%keyword%'` 의존을 줄이고 FULLTEXT 인덱스를 적용했습니다.

## 결과

| 조회 조건 | 개선 전 | 개선 후 | 개선율 |
|---|---:|---:|---:|
| 전체 조회 | 506ms | 52ms | 89.7% |
| 시도 조회 | 144ms | 22ms | 84.7% |
| 시도+구군 | 35ms | 16ms | 54.3% |
| 관광지 타입 | 223ms | 38ms | 83.0% |
| 키워드 검색 | 523ms | 4ms | 약 99.2% |
| 카페 검색 | 940ms | 34ms | 약 96.4% |

## 배운 점

- 캐시를 적용하기 전에 로그와 실행 계획으로 실제 병목을 확인할 것
- 동일한 결과라도 SQL 구조에 따라 성능이 크게 달라질 수 있음을 기억할 것
- 측정 환경과 개선 결과를 재현 가능한 수치로 남길 것
